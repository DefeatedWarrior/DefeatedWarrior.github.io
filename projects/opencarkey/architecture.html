Architecture and BLE protocol

Project Overview

OpenCarKey is a DIY keyless entry system with two components: - Firmware/LockController/ — ESP32 firmware (C++, PlatformIO) - MobileApp/ — Flutter Android/iOS app

Build & Run Commands

Mobile App

cd MobileApp
flutter pub get
flutter run                          # run on connected device
flutter build apk --release          # release APK
dart run build_runner build --delete-conflicting-outputs  # regenerate freezed files

Firmware

Open Firmware/LockController/ in PlatformIO. Use PlatformIO's Upload button or:

cd Firmware/LockController
pio run --target upload
pio device monitor --baud 115200     # serial monitor

Architecture

BLE Protocol (V4)

All app→ESP32 messages: 32-byte HMAC-SHA256 + 1-byte command + optional [length byte + data] All ESP32→app messages: 1-byte response + optional [length byte + data]

  • HMAC covers (counter_le4 || command_byte); key = SHA-256 of the password.
  • Per-device rolling counter stored in NVS (ESP32) and SharedPreferences (app). Acceptance window is counter .. counter+2 (one-sided). To reset: hold BOOT button on ESP32 for 10 seconds, or use the in-app resync flow.
  • NVS wear protection: the ESP32 keeps counters in a RAM dirty-cache (_dirtyCounters) written through to NVS on a 1.5 s debounce during the session (writeCounter/flushAllCounters) and on disconnect. The debounce is essential on a car: the ESP32 resets without a clean disconnect all the time (brownout on engine crank, watchdog, power glitch) — flushing only on disconnect rolled the counter backward on every such reset and desynced every phone. readCounter checks the dirty cache before NVS (covers quick reconnects). Both the debounced flush and the disconnect flush run on the BLE task, so there's no cross-core race on _dirtyCounters.
  • Auto-resync: on INVALID_HMAC the app silently sends RESYNC_COUNTER (HMAC proves password knowledge, payload = app's current counter) and starts a 4 s resyncTimer on BackgroundVehicle. COUNTER_RESYNCED cancels the timer (silent success → re-fetch state via GET_DATA); further INVALID_HMACs while the timer is live are ignored (collapses the connect-handshake burst into one resync). Only if the timer fires (no confirmation → genuinely wrong password) does the background emit an auth_failed event, which is the only trigger for the reset dialog. Raw INVALID_HMAC must never open the dialog directly — that surfaces a reset prompt for routine, auto-recoverable desyncs.
  • HMAC failures are rate-limited per MAC: 5 failures in 30 s → disconnect + 60 s lockout.
  • All ESP32 responses are broadcast to every connected phone (pCharacteristic->notify() has no per-connection targeting). Any per-phone filtering must happen app-side.
  • The ESP32 advertises DEVICE_NAME in plain text; the app's scan dialog filters by service UUID 0000ffe0-… (characteristic 0000ffe1-…), not by name.

Full command/response tables: Firmware/LockController/src/bluetooth/commands.h mirrored in MobileApp/lib/types/ble_commands.dart. Both files must stay in sync (verified in sync as of last audit). Same for types/features.h ↔ lib/types/features.dart.

Notable protocol semantics: - GET_DATA → LOCKED/UNLOCKED, plus current IGNITION_ON/OFF and BOOT_OPEN/CLOSED (via getIgnitionState/getBootState hooks assigned in main.cpp). Sensors otherwise only notify on change, so this is what keeps a freshly connected phone in sync. - RSSI_TRIGGER payload = [trigger float, deadZone float]. Lock (release) threshold = trigger − deadZone in dB — the dead zone is real hysteresis (it was a dead setting historically; old installs calibrated before this change may need a larger dead zone, ~10–20 dBm). - PROXIMITY_COOLDOWN payload = float minutes. - VOLTAGE (0x0E) — raw battery float, little-endian. Only sent when IGN_SENSE_ANALOG true. Current board uses false (digital opto) → never sent; app shows the key icon fallback and currentVoltage stays null.

Firmware (Firmware/LockController/src/)

  • main.cpp — pin definitions, relay pulse state machines, sensor polling, setup(), loop(). All hardware I/O lives here; assign BLE callbacks (onLocked, onUnlocked, getIgnitionState, …) in setup().
  • bluetooth/bluetooth.h/.cpp — entire BLE stack: HMAC auth, counters, proximity key, notify functions, callback/getter function pointers. Internal logic in an anonymous namespace.
  • config.h — SUPPORTED_FEATURES, DEVICE_NAME, PASSWORD, DEBUG_MODE, IGN_SENSE_ANALOG, pulse durations.
  • bluetooth/commands.h — ClientCommand / Esp32Response enums.

Timing rule: all millis() deadline comparisons must use the rollover-safe signed-difference idiom (timeReached() helper in main.cpp; (long)(deadline - millis()) > 0 pattern in bluetooth.cpp). A car install runs continuously past the 49.7-day wrap. Never write now >= deadline on raw unsigned longs.

Relay pulses are non-blocking with two slots: the main slot (_pulsePin) and the parking-light slot (_parkPin, supports N-flash sequences via _parkFlashesLeft/_parkInGap). BLE callbacks run on core 0, loop() on core 1 — the pulse variables are volatile and write-ordered (_pulseEnd before _pulsePin).

Pulse durations (config.h): lock/unlock 500 ms, boot pop 1000 ms, parking flash 250 ms with 150 ms gap (double-flash on every lock).

Features enabled in config.h control which buttons appear in the app UI. Currently enabled: DoorsLock | TrunkOpen.

Board: 303E32DC413 (4-relay + 2-optocoupler board). Confirmed by live hardware testing.

GPIO Direction Use
0 INPUT_PULLUP Boot button (counter reset, 10 s hold)
4 OUTPUT Relay 2 — Unlock (active-LOW)
5 OUTPUT Relay 3 — Parking light flash on lock (active-LOW, strapping pin — relay briefly fires at boot; hardware limitation)
13 OUTPUT Relay 1 — Lock (active-LOW)
23 OUTPUT Relay 4 — Boot pop (active-LOW)
27 INPUT_PULLUP Opto IN3 — Ignition sense (LOW = on, 200 ms poll, 2-read debounce)
33 INPUT_PULLUP Opto IN4 — Boot status (HIGH = open — opto is energised while the boot is shut; 100 ms poll, 2-read debounce)

Unused opto inputs for future use: GPIO 25 (IN1), 26 (IN2). Do not use for new relays: GPIO 0, 2, 12, 15 (strapping), GPIO 6–11 (SPI flash).

Boot-pop lock guard is app-enforced only. The firmware receives SET_TRUNK_LOCK_REQUIRE and stores it but does not gate OPEN_TRUNK — the app shows a confirm dialog when "Require Unlocked for Boot Pop" is on and the car appears locked, then sends the command unconditionally. (A firmware-side guard was removed: state drift made it block legitimate opens.)

Proximity Key (Android only)

All app logic lives in BleBackgroundService; RSSI measurement and lock/unlock triggering live on the ESP32.

ESP32 side: while autoLocking (set by PROXIMITY_KEY_ON), it polls RSSI every 500 ms (5-sample moving average) for the proximity owner (_proximityOwnerConnId / _connIdToBda; a later-connecting second phone does not steal the RSSI target). avg > trigger → unlock; avg < trigger − deadZone → lock. Proximity lock/unlock share one cooldown timestamp (previousProximityMillis, default 1 min) as oscillation protection. Three deliberate rules: 1. Every lock (manual too) arms the cooldown — so a manual lock can't be undone by a proximity unlock in the window before the app's PROXIMITY_KEY_OFF arrives. 2. PROXIMITY_KEY_ON resets the session: cooldown cleared, RSSI buffer cleared, owner re-targeted. Walking straight back after a lock-on-disconnect unlocks immediately. 3. Disconnect of the owner (or all phones) locks the car (bypassing cooldown) and clears autoLocking.

App side flow (on connect): GET_VERSION → GET_FEATURES → GET_DATA → RSSI_TRIGGER + PROXIMITY_COOLDOWN + PROXIMITY_KEY_ON → SET_TRUNK_LOCK_REQUIRE. Settings are per-vehicle (VehicleData.proximityTriggerStrength/DeadZone/Cooldown) falling back to globals — all paths that send RSSI_TRIGGER must use the effective (override-aware) values, including the global-slider handlers.

Manual-lock suppression: manual lock sets manuallyLocked on BackgroundVehicle and sends PROXIMITY_KEY_OFF; manual unlock clears it and re-sends config + PROXIMITY_KEY_ON. PROXIMITY_LOCKED (walked away) also clears it.

Ignition suppression (VehicleData.noProximityLockWithIgnition): on IGNITION_ON the app sends PROXIMITY_KEY_OFF (car must not auto-lock while ignition is on); on IGNITION_OFF it re-enables — unless manuallyLocked. Every path that would send PROXIMITY_KEY_ON (connect flow, global toggle) skips it while ignitionOn && noProximityLockWithIgnition. The PROXIMITY_LOCKED handler has a race fallback: if one still arrives, it records doorsLocked = true (the relay already fired) but skips vibration/notification.

Disconnect handling: the app computes espAutoLocked (proximity enabled, not per-vehicle disabled, not ignition-suppressed) to decide the notification text ("Proxy Locked" vs plain), the vibrate, and to set doorsLocked = true — this keeps the "car unlocked" disconnect alert from false-alarming about a car that just locked itself.

Dead zone units are dBm everywhere (global slider, per-vehicle slider, firmware). The calibration page (range_calibration.dart) streams RSSI via GET_RSSI and stores the result per-vehicle and as the global.

Mobile App (MobileApp/lib/)

State management: Riverpod. Key providers in providers/.

Two execution contexts: 1. Foreground (UI isolate) — VehicleService, SettingsService, Riverpod providers, all UI widgets. 2. Background isolate (BleBackgroundService) — Android foreground service via flutter_background_service. Owns all BLE connections, subscriptions, and proximity logic. Talks to the foreground via named events (service.invoke / service.on).

Critical: BLE operations only happen in the background isolate. The foreground never touches flutter_blue_plus directly — it calls BleBackgroundService.sendCommand() which round-trips through the background via a correlation ID (10 s timeout).

Service-channel gotcha: service.invoke payloads are JSON-serialized — a Uint8List arrives as List<dynamic>. The send_command handler converts defensively; do the same for any new binary payloads.

Data flow for a button press: 1. VehicleTile → BleBackgroundService.sendCommand(device, command) 2. Background send_command handler → BleService.sendCommand() → HMAC + counter → characteristic write 3. ESP32 response notification → _onMessageReceived → _handleMessage() updates BackgroundVehicle state + invokes foreground events; the raw message is also forwarded as command_received 4. VehicleService listens and updates Riverpod providers → UI rebuilds

UI rule: every await of BleBackgroundService.sendCommand from UI code must not let errors escape — a thrown timeout skips the setState that clears a button spinner. VehicleTile routes everything through its _sendCommand helper; fire-and-forget sites (WidgetService, calibration, dialogs) use .catchError/try-catch. Keep new call sites consistent.

Key files: - services/ble_background_service.dart — background isolate entry point, all BLE logic, proximity state machine, disconnect alerts, service event handlers - services/ble_service.dart — low-level BLE write with HMAC/counter, characteristic cache, RESYNC_COUNTER - services/vehicle_service.dart — foreground event listener, Riverpod updater, plus VehicleStorage (vehicle JSON in SharedPreferences; shared secret in flutter_secure_storage keyed secret_<mac>, migrated from legacy plaintext JSON on first load — the secret must never appear in JSON or logs) - types/background_vehicle.dart — mutable in-memory state for the background isolate (separate from the immutable Riverpod Vehicle freezed model) - types/vehicle_data.dart — persisted per-vehicle config; toJson deliberately omits sharedSecret - services/widget_service.dart — homescreen-widget state; processMessage must handle every response that a widget displays (lock, lights, engine, aux) - services/activity_service.dart — 30-day activity log in SharedPreferences; skips (not nukes) unparseable entries

Background-state invariant: reload_vehicles/_getVehicles must preserve existing BackgroundVehicle objects (update .data only). Recreating them resets live lock/ignition/boot/manual-lock state and breaks suppression + disconnect alerts.

Foreground robustness: vehicle lookups in event handlers use firstWhereOrNull — events can arrive for a just-deleted vehicle.

Disconnect Alerts (Android only)

Three independent toggles in App Settings (notifyBootOpenOnDisconnect, notifyIgnitionOnOnDisconnect, notifyUnlockedOnDisconnect, all default off) — high-priority notifications on the disconnect_alerts channel when leaving BT range with boot open / ignition on / car unlocked. Fired from _handleDisconnected, which reloads prefs first (toggles are written by the foreground isolate). Reliable because GET_DATA reports live ignition/boot state on connect.

Adding a New Protocol Command

  1. Add to ClientCommand enum in commands.h (firmware) and ble_commands.dart (app) — same value
  2. Add handler in bluetooth.cpp switch
  3. Add handler in BleBackgroundService._handleMessage() or _handleServiceEvents()
  4. If it changes UI state: add a service.invoke(...) event + a listener in VehicleService (store the subscription and cancel it in dispose) + provider setter
  5. If a homescreen widget shows the state: also handle it in WidgetService.processMessage

Known current-board limitations

  • interiorLightStream / trunkLightStream and the light/aux notify functions + callbacks are wired end-to-end but inert — those features aren't in SUPPORTED_FEATURES. They remain for future hardware.
  • Voltage sensing requires IGN_SENSE_ANALOG true (ADC divider build); the current digital-opto build never sends VOLTAGE. The "Has Voltage Sensing (ADC)" toggle in Edit Vehicle is for analog builds only.
  • Engine/windows features are unused on this board; firmware tracks no engine state (GET_DATA doesn't report it).
  • main.cpp keeps _doorsLocked/_trunkRequiresUnlocked updated even though nothing on this board consumes them (the trunk guard is app-side now).

Dependencies

Constraints in pubspec.yaml carry comments explaining every deliberate hold — read them before bumping: flutter_blue_plus stays on 1.x (2.x is commercially licensed), flutter_secure_storage stays on 9.x (10.x cipher/resetOnError defaults risk wiping stored secrets), home_widget 0.8.x is tied to the glance 1.1.1 force-pin in android/build.gradle, and flutter_local_notifications stays below 20 (breaking show() signature change). The firmware pins espressif32@^6.x — platform 7.x means an Arduino core 3 migration, done deliberately. Last full dependency review: see AUDITS.md.
